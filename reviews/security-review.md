## Confirmed vulnerabilities

### HIGH

#### H-1 — Unauthenticated read of any user's private shelf quotes
`src/lib/actions/marginalia.ts:116-127`

```ts
const records = await pb.collection("shelf_quotes").getFullList({ filter: `user = "${targetUserId}"`, ... });
if (!session || session.id === targetUserId) {
  return records;   // anonymous caller gets the target's PRIVATE quotes, unfiltered
}
```

Server actions are plain HTTP endpoints. A caller with no session cookie can invoke `getUserQuotes("<userId>")` and receive **all** of that user's `shelf_quotes` records — including quotes that were never shared with any circle — because the viewer filter (`filterQuotesForViewer`) is skipped for anonymous callers (`!session`). User ids are harvestable from public-group guest pages (member expands) or shared invite pages.

**Attack scenario:** 1) Register + join any public circle to harvest member `user` ids from the RSC payload, 2) extract the `getUserQuotes` server-action id, 3) call it with no `pb_session` cookie for each victim id → full quote text, title, attribution, tags. The `digital_marginalia` feature gate doesn't help — it's a client cookie the attacker can set (see L-5).

**Minimal fix:** require a session in `getUserQuotes` (`if (!session) return []`), and always run `filterQuotesForViewer` for `targetUserId !== session.id` — never early-return on `!session`.

#### H-2 — Any authenticated user can read the process-wide diagnostics buffer (cross-user private data)
`src/lib/actions/diagnostics.ts:6-11` + `src/lib/errors/index.ts:60-77` + `src/components/diagnostic-modal.tsx:27`

```ts
export async function getDiagnosticsAction(): Promise<DiagnosticEntry[]> {
  const session = await getSession();
  if (!session) return [];   // "Anyone authenticated can inspect diagnostics in developer mode"
  return getRecentDiagnostics();
}
```

`logDiagnostic` stores the last 50 entries **globally per process** with `technicalDetails: { ...context, ... }`, and callers routinely pass full user input: `marginalia.ts` logs `{ action: "addQuote", input }` (quote text), `progress.ts` logs `{ action: "saveMediaProgress", input }` (shelf notes/ratings), `titles.ts` logs `query`, plus raw PocketBase error payloads and stack traces. The modal is a single button on `/profile`.

**Attack scenario:** any logged-in user opens Profile → "Developer Diagnostics" → receives the last 50 error entries generated by *any* user in the same process — other members' private notes, quote text, search queries, emails in error payloads, and internal `PB_URL`/trace data.

**Minimal fix:** gate `getDiagnosticsAction` behind `requireAdmin`, and stop including raw user input in `logDiagnostic` contexts (or redact fields before logging).

### MEDIUM

#### M-1 — Guest review data (and voter identity) shipped to the client even when visibility is disabled
`src/app/groups/[groupId]/page.tsx:68`, `src/app/groups/[groupId]/titles/[titleId]/page.tsx:55`

```ts
pb.collection("titles").getFullList({ ..., expand: "addedBy,votes_via_title,reviews_via_title.user", ... });
```

Both pages fetch `reviews_via_title` (full `reviewText` + author `UsersResponse` with **email**) and `votes_via_title` (per-voter identity) unconditionally, then pass the raw records into client components. Guest-settings `visibility.reviews` / `visibility.comments` are honored only by not *rendering* tabs (`title-detail-view.tsx:377 "activeTab === 'reviews' && canViewReviews"`, `group-content-view.tsx` `avg !== null && canViewReviews && ...`). The sensitive records still travel in the RSC flight payload and embedded HTML, so any guest who can read the network response extracts full reviews/votes from a circle whose owner explicitly disabled review visibility. (Comments *are* gated server-side — `page.tsx:72-84` fetches comments only when `canViewComments` — which proves the pattern is known; reviews were missed.)

**Attack scenario:** owner disables "guests can view reviews" but keeps backlog visible; guest opens `/groups/<id>` and scrolls the RSC payload for `reviews_via_title` → all review texts + reviewer emails.

**Minimal fix:** fetch titles with `fields` minus reviews (or drop `reviews_via_title`/`votes_via_title` from `expand` when `!access.canViewReviews`); likewise only expand votes when the user is allowed to see them.

#### M-2 — CSV export is vulnerable to formula injection (spreadsheet malware)
`src/lib/exporters/csv-exporter.ts:3-14`

```ts
function escapeCsvField(val: unknown): string {
  const str = String(val);
  if (/[",\r\n]/.test(str)) return `"${str.replace(/"/g, '""')}"`;
  return str;
}
```

Quoting is RFC-4180-correct but cells beginning with `=`, `+`, `-`, `@` (e.g. a note of `=HYPERLINK("http://evil/…","click")` or `=cmd|'/C calc'!A0`) are written verbatim. A user can import via `parseCsvToTable` (`batchImportProgress`), storing `notes`/`title`/`creator` verbatim, then export CSV and open it in Excel/Sheets → formula execution on the victim's machine. Classic self-XSS/CSV-injection (CWE-1236).

**Fix:** in `escapeCsvField`, prefix `'` (or `\t`) when the trimmed value starts with `=`, `+`, `-`, `@`, `\t`, `\r`. Also strip those prefixes on import in `batchImportProgress`.

#### M-3 — `getCircleQuotes` allows unauthenticated reads for *private* circles
`src/lib/actions/marginalia.ts:139-156`

```ts
const session = await getSession();
if (session) { await requireMembership(circleId, session.id); }
// session === null → skips the membership check entirely
const records = await pb.collection("shelf_quotes").getFullList({ ... });
return records.filter((q) => Array.isArray(q.isSharedWithCircles) && q.isSharedWithCircles.includes(circleId));
```

With no session, the caller only needs the circle id (unguessable but obtainable from an invite link or from a shared quote record) to read every quote this circle was shared with — even for a fully private group. Quoted-in-circle means "visible to this circle's members", and there is no "public group" carve-out checked.

**Fix:** `requireMembership(circleId, session.id)` unconditionally (or allow guests only for public groups), and return `[]` when unauthenticated.

#### M-4 — Open redirect / OAuth `redirect_uri` tampering via trust of forwarded host headers
`src/lib/pocketbase/session.ts:87-113` (`getRequestOrigin`), `src/proxy.ts:21-25`, `src/app/api/auth/oauth2-callback/route.ts:22-24`

```ts
const host = req.headers.get("x-forwarded-host") || req.headers.get("host");
const proto = req.headers.get("x-forwarded-proto") || "https";
if (host && !host.includes("0.0.0.0")) return `${proto}://${host}`;
```

`getRequestOrigin` accepts `x-forwarded-host`/`x-forwarded-proto` verbatim and every redirect (middleware `-> /login`, OAuth `deny()`, successful callbacks) is built on that origin. This is only safe if the deployment's reverse proxy *guarantees* it strips/overwrites client-supplied forwarded headers (an attacker can otherwise set `x-forwarded-host: evil.example` on any request). The OAuth flow is the highest stake: with a spoofable host used in `redirectUri` (`oauth2RedirectUrl`), `authWithOAuth2Code` is performed against the attacker-chosen URI — a host-header OAuth code/token leakage primitive when the proxy config is permissive.

**Fix:** validate the computed origin against an explicit allowlist — prefer `process.env.APP_URL` when set, ignore `x-forwarded-*` unless the proxy is configured to overwrite them (document it), and reject/normalize `Host` values not matching the deployed domain.

### LOW / hardening

#### L-1 — PB filter string interpolation (injection surface, not yet attacker-controlled)
- `src/lib/actions/progress.ts:68` — `filter += \` && status = "${statusFilter}"\``; `statusFilter` is a caller-supplied argument to a callable server action. Today it is only invoked with `undefined` (`shelf/page.tsx:20`), and the caller only hits their own `user = session.id` rows, so blast radius is self-only — but a crafted `statusFilter` (`in_progress" || true`) can distort the query and is a landmine the moment any other caller uses it.
- `src/lib/actions/marginalia.ts:120,131` — `` user = "${targetUserId}" `` interpolation (see H-1; ids are PB-generated so not directly injectable, but the pattern invites regressions).
- `src/lib/actions/schedules.ts:103` — `` schedule = "${id}" `` in a raw OR-joined filter.

**Fix:** route all of these through `pb.filter("{:id}", ...)` parameter binding like the rest of the codebase already does.

#### L-2 — Blind-pick redaction only covers `addedBy`; voter/reviewer identity remains in payload
`src/lib/moods.ts:151-179` (`redactProposedTitles`), applied at `groups/[groupId]/page.tsx:119` and title page `:89`. The server-side shallow-copy correctly strips `addedBy` for non-owner/admins, but `expand.votes_via_title` (per-voter user ids) and `reviews_via_title` (reviewer identity + text) still ship to every blind-pick viewer, so "who did what" around the pick is still fully observable even though the proposer is redacted. Align semantics: if blind-pick should hide participation, drop/redact those expands too (and note `votes` `user` field leakage in the RSC stream regardless of `canViewReviews`).

#### L-3 — Public circles expose members' progress notes/ratings to guests
`src/lib/actions/progress.ts:380-406` (`getTitleCircleProgress`) and `:408-427` (`getCircleLiveActivity`): a guest of any public group gets every member's `user_media_progress` record (including `notes`, `rating`, `moods`) whenever `p.isSharedWithCircles !== false` — and `saveMediaProgress` defaults `isSharedWithCircles ?? true` (`progress.ts:155`), i.e. sharing is opt-out, not opt-in. Confirm this is intended; otherwise gate guest access to public groups with explicit per-record opt-in or a guest-visibility setting.

#### L-4 — No application-level rate limiting on auth-facing actions
`signInWithEmail` (server action `auth.ts:118-141`, creates a user on every unknown email — **unlimited account creation** by design), `signUpWithPassword`, `requestPasswordReset`, `verifyEmailCode`, `signInWithPassword`, and `joinGroupByCodeAction` have no throttling; the app relies entirely on PocketBase's built-in per-endpoint auth limits. Missing: auth-endpoint rate limiting (IP/email), CAPTCHA/reCAPTCHA on signup, and OTP retry backoff. Also `signUpWithPassword` returns a distinct `EmailInUse` error (`auth.ts:174-176`) — mild account enumeration, acceptable for standard signup UX but worth noting.

#### L-5 — Feature flags are client-controlled, so `requireFeature` is not a security boundary
`src/lib/flags/actions.ts` (`toggleUserFeatureFlag`) lets *any* user write `titirek_flags`/`flag_<key>` cookies, and `requireFeature("digital_marginalia")` (`marginalia.ts:35,81,142,175`) is resolved from those same cookies (`flags/server.ts:96-120`). Anyone can self-enable the quotes feature. Not exploitable today because record-level ownership checks are intact, but treat flags strictly as UX gating — never as an access control.

#### L-6 — Ops notes
- `docker-compose.yml` default `PB_URL=${PB_URL:-http://localhost:8090}` points at the container's own localhost while the prod fallback in code is `http://pocketbase:8090` (`session.ts:20-22`) — misconfig-prone; align the compose default with the code fallback.
- No hardcoded secrets found (`docker-compose.yml` reads `PB_SUPERUSER_*` from env, `.env*` gitignored, keys referenced server-side only in `lib/providers/` and `superuser.ts`); no `dangerouslySetInnerHTML` anywhere (`grep` = 0 hits); users collection is create-locked to superusers (`pb_migrations/1755280800_initial_schema.js`, rules null) so signup must go through server actions.
- `logDiagnostic` stashes raw user input + full stack traces in memory for 50 entries and on console — pair with H-2 fix; consider `NODE_ENV`-gated stack capture.

## Verified-good (evidence)

- **Guards on every mutating title path:** `markConsumed`/`unmarkConsumed` (`titles.ts:160-167,182-189`) → `requireMembership` + `requireTitleInGroup`; `addComment` (`comments.ts:24-26`) → `resolveCircleAccess.canComment` + `requireTitleInGroup`; `submitReview` (`reviews.ts:23-26`) → `canReview` + `requireTitleInGroup`; `voteOnTitle` (`votes.ts:25-28`) → `canVote` + `requireTitleInGroup`; `toggleMilestoneCheckin` (`schedules.ts:301-304`) → `requireMembership` + `requireMilestoneInGroup` (which validates the milestone's *schedule's* group, `membership.ts:152-165`).
- **Cross-resource checks:** `removeMember` verifies `target.group === groupId` (`groups.ts:283`); `deleteComment` verifies `comment.group === groupId` (`comments.ts:124-128`); `deleteMilestoneComment` same (`schedules.ts:395-397`); sagely they re-check the *target* record, not just the passed `groupId`.
- **Progress records are owner-scoped:** `saveMediaProgress`/`updateProgressQuickStep`/`deleteMediaProgress` all compare `existing.user === session.id` (`progress.ts:181-186,229-232,255-259`); the only group cross-link (`groupTitle`) is guarded by `requireMembership(titleRecord.group, session.id)` (`progress.ts:165-171`).
- **Admin surface:** both middleware (`proxy.ts:27`) and the layout server-side `requireAdmin(session.id)` per render (`admin/layout.tsx:14-16`), plus `requireAdmin` in every admin action (`admin.ts`).
- **Session hygiene:** cookie is `httpOnly`, `secure` in prod, `sameSite: lax`, 5-day TTL (`session.ts:63-75`); token re-validated against PB on every request, so bans are ~instant; OAuth state + PKCE `codeVerifier` are server-entropy from PB and validated with constant-ish comparison in callback (`oauth2-callback/route.ts:33-40`); OTP cookie is httpOnly/5-min and consumed once; invite codes are CSPRNG 40-bit (`invite-code.ts`) with 5 retry-on-collision loops.
- **Input constraints:** mood/pace normalization to allow-lists (`moods.ts`), rating `1..5` integer (`reviews.ts:28-32`), comment 1..2000 chars (`comments.ts:7-19`), lengths capped everywhere; `coverUrl` restricted to `http(s)` (`titles.ts:82,122`).

## Top 5 security fixes worth doing now

1. **Gate `getUserQuotes` behind a session and always apply the viewer filter for other users** — closes the unauthenticated private-quotes endpoint (H-1). One `if (!session) return []` + moving the early return to `session.id === targetUserId` only.
2. **Restrict diagnostics to admins and stop logging raw user input** in `logDiagnostic` contexts (H-2) — the cross-user PII dump behind a profile button is the easiest genuine privacy breach in the app.
3. **Honor `canViewReviews` server-side**: drop `reviews_via_title` (and, under blind-pick, `votes_via_title`) from the title/group `expand` when the viewer isn't allowed to see them (M-1). This matches the pattern already used for comments.
4. **Neutralize formula-leading characters in CSV export** (`escapeCsvField`), so notes like `=HYPERLINK(...)` can't weaponize exported files (M-2).
5. **Harden `getRequestOrigin`** — validate the effective host against `APP_URL`/an allowlist instead of trusting `x-forwarded-host`/`Host` verbatim, and document the proxy header contract (M-4). Cheap, removes the OAuth/open-redirect primitive at the root of several trust chains.

## Residual risks (unaddressed or intent-dependent)

- Guest/share semantics: quotes shared by circle id, member progress visible to public guests, schedules w/ titleRecord visible to guests — verify against product intent (L-3, M-3).
- Blind-pick scope vs. vote/review identity leakage (L-2).
- No auth rate limiting at the app layer (L-4).
- Deployment-dependent trust of forwarded headers (M-4) and the compose `PB_URL` default (L-6).
- Feature-flag cookie gate is bypassable by design (L-5).
- Static review only; no tests executed (read-only mandate), no live PB to confirm OTP/password throttling defaults.
